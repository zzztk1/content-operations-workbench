# 项目2从 0 到 1 复现执行方案（v1）

最后更新：2026-04-09

## 1. 这份文档的作用

这份文档只做一件事：

> 把项目2严格适配到“AI 产品经理从 0 到 1 复现项目通用路径”。

也就是说，后续项目2主线程不再按我自己的压缩顺序推进，而是统一按下面这条主线走：

1. 需求分析
2. 模型预研
3. 数据准备
4. 模型设计
5. 模型对齐
6. 模型应用
7. 模型评测
8. 模型上线
9. 验收测试
10. 发布上线
11. 持续运营

## 2. 项目2能不能按这条路径完整复现

结论：**能。**

但要说清楚“能”的含义：

- 能按这条路径完整推进项目2
- 能覆盖项目2当前锁定的核心目标
- 能让每一步都产出文档、结果和面试稿

同时也要保留真实边界：

- 个别高成本或环境相关事项，例如某些外部模型供应商、某些并发增强细节，后续仍可能需要单独确认
- 但这不影响项目2整体按这条路径复现

所以后续口径统一为：

> 项目2完全按通用路径复现，只是在每一步里的任务内容会根据“工作流系统”这个项目特点做专门适配。

## 3. 项目2一句话定位

> 一个面向自媒体内容运营场景的、可恢复、可审批、可回查、可测量的 Graph RAG 内容工作流系统。

## 4. 项目2总目标

项目2这次不是继续维护旧的“自定义状态机 + SQLite checkpoint”版本，而是要把它升级为：

- 真 `LangGraph StateGraph`
- 真 `PostgreSQL Checkpointer`
- 有 `SubGraph`
- 有 `Mock` 开关体系
- 有 `SlowAPI`、`/health`、`graceful shutdown`
- 有 `JSON Mode + 手动解析 + Pydantic 校验`
- 有 `SSE / astream_events` 级流式输出
- 有 `before / after` 基线测量

## 5. 项目2按通用路径的逐步适配

## Step 1：需求分析

### 这一步在项目2里要做什么

- 回答为什么做这个项目
- 回答为什么用大模型
- 回答为什么不用成熟 SaaS
- 回答为什么不用 Coze / Dify 作为最终方案
- 做竞品分析
- 输出 PRD
- 输出用户流程图

### 这一步的产物

- 需求分析文档
- 竞品分析文档
- PRD
- 用户流程图

### 这一步的验收标准

- 你能说清楚项目2不是“AI 写作工具”，而是“内容工作流系统”
- 你能说清楚目标用户、核心场景、MVP 和非目标
- 你能说清楚为什么最终选择自研而不是直接用平台方案

### 当前适配状态

- 已开始
- 已有需求分析、PRD、用户流程、竞品材料基础
- 后续主线程继续严格按这个顺序推进

## Step 2：模型预研

### 这一步在项目2里要做什么

这里的“模型预研”不是只看基座模型，而是看整套 AI 工作流底座：

- 主模型选型（当前主线为阶跃星辰 API）
- 平台适配是否需要模型路由
- `LangGraph` 是否作为编排框架
- `PostgreSQL Checkpointer` 是否作为持久化底座
- `JSON Mode` 是否适合关键节点
- 是否保留其他供应商作为可选增强

### 这一步的产物

- 模型与框架选型说明
- 备选方案对比
- 不可乱写的术语边界

### 这一步的验收标准

- 你能说清楚为什么选这条技术路线
- 你能说清楚哪些词能写、哪些不能先写

### 项目2里的重点

- `LangGraph`
- `PostgreSQL`
- `JSON Mode`
- `Pydantic`
- `SlowAPI`

## Step 3：数据准备

### 这一步在项目2里要做什么

项目2虽然不是典型 RAG 问答系统，但仍然有 4 类关键数据要准备：

- 样本内容数据（用于 research / writer）
- 评测数据（用于 workflow 验证）
- badcase 数据（用于重写和后续优化）
- 测量数据（用于 baseline / optimized 对比）

### 这一步的产物

- 样本库说明
- 基线评测数据
- benchmark 输入约定
- 结果文件命名规范

### 这一步的验收标准

- 你能说清项目2不是“没数据的纯工作流”
- 你能说明哪些数据支持研究、哪些数据支持评测、哪些数据支持简历结果

## Step 4：模型设计

### 这一步在项目2里要做什么

模型设计在项目2里主要体现为：

- 节点职责设计
- `State`（状态）设计
- `StateGraph`（状态图）设计
- `SubGraph`（子图）拆分
- 各节点输入输出协议设计

### 这一步的产物

- 节点与状态设计文档
- LangGraph 结构设计文档

### 这一步的验收标准

- 你能说清每个节点负责什么
- 你能说清为什么要拆子图
- 你能说清为什么 reviewer 和 approval 不能合并

## Step 5：模型对齐

### 这一步在项目2里要做什么

项目2里的“模型对齐”，主要不是做聊天风格对齐，而是让各节点输出更稳定、更可控：

- research 输出结构化候选主题
- writer 输出结构化草稿
- reviewer 输出结构化评分与反馈
- adapter 输出结构化平台化内容
- 关键节点采用 `JSON Mode + 手动解析 + Pydantic 校验`

### 这一步的产物

- 节点 schema 设计
- JSON fallback 方案
- 错误恢复机制

### 这一步的验收标准

- 至少有关键节点结构化输出约束
- 至少有失败恢复路径

## Step 6：模型应用

### 这一步在项目2里要做什么

这是项目2真正开始“落系统”的阶段，而且这一阶段不能只停留在设计和骨架层。

在项目2里，只有当新版 MVP 真正跑通以后，才能认为这一步完成；否则只能算“进行中”。

这里说的 MVP，至少要满足：

- 保留旧版 baseline
- 在新目录下搭 `LangGraph v2` 骨架
- 真接入主图和至少一个 `SubGraph`
- 真接入阶跃星辰 API 主模型链路
- 关键节点真接入 `JSON Mode + 手动解析 + Pydantic`
- 真接入 `PostgreSQL Checkpointer`
- 真保留审批、导出和 run 回查语义
- 至少提供一个可运行入口（脚本或 API）
- 至少完成一次端到端运行验证

### 这一步的产物

- LangGraph 代码
- Postgres checkpointer 代码
- mock 配置骨架
- API 入口或可运行脚本
- 最小 MVP 跑通记录
- 新版运行结果文件

### 这一步的验收标准

- 不破坏旧版可运行基线
- 新版 graph 能独立运行
- 新版主链路至少完成一次端到端执行
- 至少能证明 `brief -> research -> writer -> reviewer -> approval/export` 这条链路在新版里能走通
- 没跑通 MVP 之前，不进入 Step 7 模型评测

## Step 7：模型评测

### 这一步在项目2里要做什么

- 保留旧版 functional baseline
- 对比状态机版与 LangGraph 版
- 测 `ttft`、`node_latency`、`total_latency`
- 测 schema pass rate、fallback trigger rate
- 测 SSE 流式体验

### 这一步的产物

- baseline 报告
- optimized 报告
- compare 报告

### 这一步的验收标准

- 每个高价值亮点都有实现动作、测量动作、结果文件
