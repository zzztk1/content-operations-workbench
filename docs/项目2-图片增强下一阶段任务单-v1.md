## 2. 下一阶段最该做的事情

这一步只做图片增强，不回头改文本主线。

### 2.1 第一优先级：把图片并发能力接到产品链路

目标：

- 不只停留在 benchmark 脚本里支持并发
- 让用户侧或 API 侧能实际触发多图生成

建议实现：

1. 新增图片批量生成入口
2. 支持一次生成 2 到 4 张封面候选图
3. 支持返回候选图列表和首选图
4. 导出结果中保留图片候选集元数据

验收指标：

- 能通过 API 或工作流参数触发多图生成
- 单次运行的导出结果里包含候选图数组
- 前端至少能展示首图和候选图数量
- 结果文件新增真实多图运行样例

### 2.2 第二优先级：补图片侧 before / after 评测闭环

目标：

- 让图片优化也满足“实现动作 + 测量动作 + 结果文件”

建议实现：

1. 固定一组图片 prompt 样本
2. 对比串行和并发
3. 记录 wall time、平均单图延迟、失败率、重试次数
4. 输出统一 compare 报告

验收指标：

- 生成 `before / after` 图片 compare 报告
- 报告里至少包含：
  - `total_elapsed_ms`
  - `avg_asset_latency_ms`
  - `retry_count`
  - `success_rate`
  - `speedup_ratio`
- 报告可以直接支撑简历表述

### 2.3 第三优先级：补图片稳定性与质量校验

目标：

- 不只是“生成了一张图”，还要判断图片可用

建议实现：

1. 扩展图片质量校验报告
2. 检查图片尺寸、宽高比、文件格式、文件大小
3. 如果能低成本实现，可加入基础图文一致性检查占位

验收指标：

- 质量报告至少包含：
  - 尺寸
  - 宽高比
  - mime type
  - file size
- 对异常图片有明确失败标记

### 2.4 第四优先级：补图片体验层

目标：

- 让 `/demo` 不只是显示一张最终图，而是更像真实封面生成体验

建议实现：

1. 支持显示候选图列表
2. 标出主图
3. 展示图片生成耗时
4. 展示图片模型与图片尺寸

验收指标：

- `/demo` 中能看到至少 2 张候选图时的展示形态
- 能看到图片侧关键指标

## 3. 这一步不做什么

为了控制范围，这一轮不做：

1. 多模型动态路由
2. 图片编辑能力
3. 复杂视觉语义审核
4. 云端生产部署优化
5. 为了贴术语而做的低收益改造

## 4. 推荐执行顺序

1. 先把多图候选生成接进 API / workflow
2. 再补图片 compare 报告
3. 再补图片质量校验字段
4. 最后补 `/demo` 展示
