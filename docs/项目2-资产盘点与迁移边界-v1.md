# 项目2资产盘点与迁移边界（v1）

最后更新：2026-04-09

## 1. 目的

这份文档专门回答三个问题：

1. 旧版项目2里到底有什么资产
2. 哪些资产可以复用到 LangGraph 版本
3. 哪些必须重做，不能继续沿用

## 2. 当前真实基线

当前项目2是一个**可运行、可验证、可演示**的状态机版基线：

- 主链路：`brief -> research -> writer -> reviewer -> approval -> export`
- 重写回路：review score 不达标时可重写
- 审批分支：`approve / needs_edit / reject`
- 持久化：SQLite checkpoint
- 产物导出：JSON + Markdown
- 指标：latency / token / cost / error
- 验证：3 条路径通过

这说明：

- 旧版已经有很好的业务闭环
- 但它不是原版 PDF 需要的技术路线

## 4. 旧版节点逻辑：哪些可直接迁移

### 4.1 Research 节点

可复用：

- 输入：`brief + platform`
- 输出：`topics`
- 失败降级：没有 topics 时生成 fallback
- trace / metrics 记录方式

需要升级：

- research 要支持更明确的 evidence merge
- 需要结构化 schema
- 后续要支持 SubGraph 和外部检索增强

### 4.2 Writer 节点

可复用：

- 输入：`selected_topic + style + feedback + references`
- 输出：`title / content / tags`
- 重写回路接收 reviewer feedback

需要升级：

- 输出协议需更严格
- 需要 JSON Mode + manual parse + schema 校验
- 后续要支持模型路由

### 4.3 Reviewer 节点

可复用：

- 评分三元结构：`attraction / accuracy / platform`
- 总分阈值逻辑
- feedback 回流机制

需要升级：

- reviewer 结果要完全结构化
- 需要显式 schema 校验
- 可补 request/node/model 级 metrics

### 4.4 Adapter 节点

可复用：

- 平台适配责任
- 小红书免适配的逻辑

需要升级：

- 可以并入 Writing SubGraph
- 输出结构需要统一
- 若做并发增强，可作为并发切入点

### 4.5 Approval 节点

可复用：

- `approve / needs_edit / reject`
- `approval_note`
- `approval at`

需要升级：

- 要与 review/approval subgraph 路由统一
- 要支持历史恢复语义

### 4.6 Export 节点

可复用：

- JSON / Markdown 内容包结构
- 导出路径格式

需要升级：

- 导出物里可补 request_id / metrics 摘要 / graph version

## 5. 当前设计中最值得保留的部分

如果只看旧版代码，最值得保留的不是“类名”，而是这四种产品语义：

1. 节点职责分得比较清楚
2. review -> rewrite 的回路是对的
3. approval 分支是对的
4. export 和 run_id 回查已经形成用户可感知闭环

这些语义应该进入 LangGraph 版本，而不是被推翻。

## 6. 当前设计中最容易误导的部分

旧资产里最容易让后续复现跑偏的点有三个：

### 6.1 文档里默认把 LangGraph 当成已实现

旧 [PRD.md](F:/codex/codex1/projects/media-agent/docs/PRD.md) 和 [Agent工作流设计.md](F:/codex/codex1/projects/media-agent/docs/Agent工作流设计.md) 默认以目标态在写，但当前真实代码不是 LangGraph。

结论：

- 这些文档可以当“目标态参考”
- 不能当“当前已实现事实”

### 6.2 SQLite checkpoint 很像“已经完成持久化”

它确实完成了旧版持久化，但不能等同于原版要求的 Postgres Checkpointer。

### 6.3 功能验证报告容易被误读为性能报告

[latest_validation_report.json](F:/codex/codex1/projects/media-agent/benchmarks/latest_validation_report.json) 当前更像功能基线，而不是可直接写进简历的性能基线。

## 7. 迁移边界

### 7.1 必须保留的业务边界

- 不取消人工审批
- 不取消 export
- 不取消 run_id 回查
- 不把系统降级成单轮问答

### 7.2 必须改变的工程边界

- 从手写流程改为 LangGraph 主图 + 子图
- 从 SQLite 改为 Postgres Checkpointer
- 从同步闭环改为支持事件流
- 从单一 `LLM_MOCK` 改为多 mock 开关
- 从宽松 JSON 提取改为结构化校验链

### 7.3 暂不擅自改变的部分

- 不改业务方向
- 不切换到别的项目场景
- 不把低价值高成本点包装成既成事实

## 8. 旧版 baseline 的正确用途

旧版的正确定位应该是：

- 业务基线
- 功能基线
- 演示基线
- 迁移对照组

而不是：

- 最终版
- 原版路线完成版
- 可直接照抄进最终简历的工程形态

## 9. 结论

项目2旧版最大的价值不是“已经做完”，而是它已经帮我们证明：

- 业务闭环成立
- 用户主流程成立
- 节点职责成立

因此接下来的正确推进方式不是从零瞎写，而是：

> 保留业务语义，重做图编排、持久化、流式输出、校验与测量体系。
