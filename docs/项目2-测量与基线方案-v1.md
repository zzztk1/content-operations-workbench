# 项目2测量与基线方案（v1）

最后更新：2026-04-09

## 1. 目的

项目2后续任何能写进简历的优化项，都必须同时具备：

- 实现动作
- 测量动作
- 结果文件

这份文档用于定义：

- 旧版 baseline 怎么留
- 新版优化怎么测
- `benchmarks/` 目录未来怎么组织

## 2. 当前已有基线：能用什么，不能用什么

## 2.1 当前已有结果

已存在结果文件：

- [latest_validation_report.json](F:/codex/codex1/projects/media-agent/benchmarks/latest_validation_report.json)

它当前能证明：

- 3 条关键路径能跑通
- 导出产物存在
- 基础 metrics 字段存在

## 2.2 当前已有结果不能直接证明什么

它**不能直接作为最终性能结论**，因为：

- 当前运行在 `LLM_MOCK=true`
- latency 非真实模型延迟
- 没有 streaming 指标
- 没有 TTFT
- 没有 before / after 对照组

结论：

- 当前报告是**功能基线**
- 不是最终性能基线

## 3. 项目2后续必须测的指标

### 3.1 Functional baseline

用于证明“链路没坏”：

- `approve -> completed`
- `needs_edit -> needs_manual_edit`
- `reject -> rejected`
- export exists
- trace exists

### 3.2 Runtime baseline

用于证明“系统性能和稳定性”：

- `total_latency_ms`
- `node_latency_ms`
- `ttft_ms`
- `error_count`
- `retry_count`

### 3.3 Output baseline

用于证明“结构化输出可用”：

- schema pass rate
- JSON parse fail rate
- fallback trigger rate

### 3.4 Operational baseline

用于证明“服务具备最小工程能力”：

- `/health` success rate
- rate limit behavior
- graceful shutdown behavior
- mock / real mode switch behavior

## 4. before / after 对照规则

每个高价值改动都必须按以下格式做对照：

### 4.1 改动前

- baseline 脚本
- baseline 数据
- baseline 结果文件

### 4.2 改动后

- optimized 脚本或同脚本新参数
- optimized 数据
- optimized 结果文件

### 4.3 对比结果

- compare 报告
- 明确提升 / 退化 / 持平

## 5. benchmarks 目录规则

建议未来演进为：

```text
benchmarks/
  validate_workflow.py
  latest_validation_report.json
  baselines/
    state_machine_v1/
    langgraph_pg_v1/

    latest/

```

## 5.1 baselines

存放不同阶段的原始结果：

- `state_machine_v1`：旧版状态机基线
- `langgraph_pg_v1`：LangGraph + Postgres 首轮基线

## 5.2 reports

存放阶段性报告：

- functional report
- latency report
- streaming report
- health / rate limit report

## 5.3 compare

存放 before / after 对照结果：

- graph migration compare
- streaming compare
- JSON validation compare
- health / rate-limit compare

## 6. 第一批必须落地的测量项

### 6.1 Graph migration

目标：

- 对比旧版状态机和 LangGraph 版本在功能正确性上是否一致

必须输出：

- functional baseline
- functional optimized
- compare report

### 6.2 PostgreSQL Checkpointer

目标：

- 验证 Postgres checkpointer 是否完成保存 / 恢复 / 回查

必须输出：

- save / load / recover 验证结果
- compare report

### 6.3 Streaming

目标：

- 验证 non-stream 与 stream 的用户感知差异

必须输出：

- `ttft_ms`
- `total_latency_ms`
- 事件流样例
- compare report

### 6.4 JSON validation

目标：

- 验证结构化输出在严校验后是否更稳

必须输出：

- schema pass rate
- parse fail rate
- fallback rate
- compare report

### 6.5 Health / Rate Limit

目标：

- 验证 `/health` 可用
- 验证 rate limit 生效
- 验证 graceful shutdown 行为

必须输出：

- health check result
- limit trigger result
- shutdown behavior notes

## 7. 结果文件命名建议

建议用：

```text
<date>-<scope>-baseline.json
<date>-<scope>-optimized.json
<date>-<scope>-compare.md
```

例如：

```text
2026-04-09-graph-functional-baseline.json
2026-04-10-graph-functional-optimized.json
2026-04-10-graph-functional-compare.md
```

## 8. 结果文件最小字段建议

JSON 报告至少包括：

- `generated_at`
- `scenario`
- `mode`
- `mock_flags`
- `metrics`
- `status_summary`
- `notes`

如果是 compare 报告，还要包括：

- `before_file`
- `after_file`
- `improvement_summary`
- `risks`

## 9. 当前阶段建议结论

这一轮不急着造很多脚本，先把规则定住。

原因是：

- 旧版已有 functional baseline
- 新版还没正式接入 LangGraph / Postgres
- 此时先把测量口径统一，比先多写几个零散脚本更值钱

## 10. 当前最重要的门禁

从现在开始，项目2里任何一句结果型表述都要先问 3 个问题：

1. 有没有实现动作？
2. 有没有测量动作？
3. 有没有结果文件？

少一个，都不进入最终简历口径。
