# 项目2阶段1：模型预研

最后更新：2026-04-09

## 1. 这一步要解决什么问题

项目2的“模型预研”，不是只回答“选哪个大模型”，而是回答：

- 哪个模型负责内容生成与审核
- 哪个框架负责把多节点任务编排起来
- 哪种持久化方式支撑恢复执行
- 哪种结构化输出方案最适合这个系统
- 哪些能力现在可以写，哪些还不能先承诺

换句话说，项目2里的模型预研，本质上是在确定：

> 这个内容工作流系统的智能底座和运行底座到底怎么选。

## 2. 先解释几个会反复出现的词

- `LLM`（Large Language Model，大语言模型）：负责理解、生成、改写、审核内容的模型。
- `OpenAI-Compatible API`（OpenAI 兼容接口）：接口形式和 OpenAI 类似，便于切换模型供应商。
- `LangGraph`：基于图结构组织大模型工作流的编排框架。
- `Checkpointer`（状态持久化器）：把运行过程中的状态保存下来，方便恢复和回查。
- `JSON Mode`（JSON 输出模式）：尽量让模型直接输出标准 JSON。
- `Pydantic`：Python 里的数据结构校验工具，用来验证模型输出是不是符合约定格式。
- `SlowAPI`：FastAPI 体系里常用的限流组件，用于控制接口访问频率。

## 3. 项目2为什么不能只做“模型选型”

项目2和项目1最大的区别之一是：

- 项目1更像“模型 + 检索 + 对话体验”
- 项目2更像“模型 + 工作流 + 状态恢复 + 工程治理”

所以项目2在预研阶段，必须同时考虑 4 层：

1. 生成与审核模型层
2. 工作流编排层
3. 状态持久化层
4. 结构化输出与稳定性层

## 4. 生成模型预研

## 4.1 项目2对生成模型的要求

项目2里模型至少要能完成这些事：

- 根据 brief 生成候选选题
- 按平台风格生成内容
- 对内容做结构化审核
- 根据反馈重写
- 稳定输出 JSON

所以这里最看重的不是“谁最强”，而是：

- 中文内容生成质量
- 稳定性
- 成本
- 是否支持 OpenAI 兼容接口
- 是否适合结构化输出

## 4.2 当前推荐基线

当前项目2的推荐基线是：

- 接入 `阶跃星辰 API`（StepFun API）
- 通过 OpenAI 兼容接口方式完成模型调用

原因：

- 中文能力和内容生成质量适合项目2场景
- 兼容接口方式更利于后续工作流迁移
- 便于统一 writer / reviewer / adapter 的模型调用方式

## 4.3 可选增强

### 其他供应商路线

定位：

- 可选增强，不是主线硬依赖

适合补的时机：

- 主链路稳定之后
- 想让术语和原版更接近时

现在为什么不直接绑定其他供应商：

- 不应该为了模型名破坏主线推进
- 供应商不是项目价值本身

## 5. 工作流框架预研

## 5.1 为什么项目2必须真迁 `LangGraph`

项目2不是“模型调用 + if/else”就够的项目，它需要：

- 多节点协作
- 条件分支
- 重写回路
- 审批分支
- 状态恢复
- 流式事件

这类场景非常适合 `StateGraph`（状态图）这种图式工作流。

所以这里不是“可选尝试”，而是：

- **必须真迁 `LangGraph StateGraph`**

## 5.2 为什么不继续沿用手写状态机

旧版手写状态机的优点是：

- 已经证明业务闭环可行

但它的问题是：

- 扩展性有限
- 很难自然承接子图
- 不适合原版术语表达
- 和后面的 `Checkpointer`、事件流、可观测性不够顺畅

结论：

- 旧版可作为 baseline
- 但不能作为最终技术路线

## 6. 状态持久化预研

## 6.1 为什么要从 SQLite 升级到 PostgreSQL

SQLite 的价值：

- 轻量
- 本地演示方便
- 适合旧版 baseline

但项目2后面要承接的是：

- `Checkpointer`
- 恢复执行
- 历史回查
- 更接近真实服务场景的运行方式

在这个目标下，`PostgreSQL` 更合适。

## 6.2 `PostgreSQL`（关系型数据库）在项目2里的角色

它不是用来做业务搜索库，而是用来做：

- 运行状态保存
- 恢复执行
- 历史线程管理

所以这里的关键不是“数据库换一个”，而是：

> 把“状态持久化”从手写实现升级成与图工作流更匹配的运行时能力。

## 7. 结构化输出预研

## 7.1 为什么项目2必须重视结构化输出

项目2不是一个只要“看起来像内容”就行的系统。

它很多节点都需要严格结构：

- research 要输出 topics
- writer 要输出 title / content / tags
- reviewer 要输出 score / feedback / passed
- adapter 要输出平台化结果

如果结构不稳定，后面就会影响：

- 路由判断
- 重写回路
- 审批逻辑
- 导出逻辑

## 7.2 推荐方案

项目2当前推荐使用三层方案：

1. `JSON Mode`
2. `json.loads` / 手动提取
3. `Pydantic` 校验

原因：

- 只靠 prompt 要求 JSON 不够稳
- 只做手动提取不够严
- 只做黑盒 structured output 又不利于解释和排错

所以这套方案最适合项目2这种要兼顾稳定性和可解释性的系统。

## 8. 稳定性底座预研

这部分虽然看起来不像“模型”，但在项目2里必须在预研阶段一起定。

## 8.1 为什么要提前定 `SlowAPI`

因为项目2不是脚本，而是后面会走向 API 化的系统。

一旦进入 API 化，就必须提前考虑：

- 接口访问频率控制
- 滥用保护
- 最小线上运行安全

所以 `SlowAPI` 不应该等到最后补，而应该从预研阶段就锁定为默认方案。

## 8.2 为什么要提前定 `/health`

`/health`（健康检查接口）不是为了好看，而是为了判断：

- 服务起没起来
- 关键依赖是否可用
- 后面怎么做自动化验证

## 9. 方案对比结论

| 维度 | 基线推荐 | 备选 | 当前结论 |
|---|---|---|---|
| 内容生成模型 | 阶跃星辰 API（StepFun API） | 其他兼容供应商 | 先用阶跃星辰跑通主线，后续再评估增强 |
| 工作流框架 | LangGraph StateGraph | 手写状态机 | 必须真迁 LangGraph |
| 状态持久化 | PostgreSQL Checkpointer | SQLite 手写持久化 | 必须真迁 PostgreSQL |
| 结构化输出 | JSON Mode + 手动解析 + Pydantic | 宽松 JSON 提取 | 必须升级为严格方案 |
| 限流 | SlowAPI | 自写限流 | 先锁定 SlowAPI |

## 10. 哪些词现在可以写，哪些不能先写

### 现在可以写成目标路线

- `LangGraph`
- `StateGraph`
- `PostgreSQL Checkpointer`
- `JSON Mode`

### 当时还不能写成已完成事实

原因：

- 这些还没有正式跑出实现、测量和结果文件

## 11. 本阶段验收标准

- 你能说清为什么当前主线选择阶跃星辰 API，而不是一开始就绑定多个供应商。
