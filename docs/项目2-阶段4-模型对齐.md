# 项目2阶段4：模型对齐

最后更新：2026-04-09

## 1. 这一步要解决什么问题

模型设计已经确定了：

- 节点怎么拆
- 状态怎么流转

模型对齐这一步要继续解决的是：

- 怎么让每个节点输出得更稳定
- 怎么让系统更容易消费模型结果
- 当模型输出不稳定时，系统怎么兜底

对项目2来说，模型对齐的核心不是“让模型更像人说话”，而是：

> 让模型在 workflow（工作流）里输出更可控、更结构化、更容易路由的结果。

## 2. 先解释几个关键词

- `JSON`：一种结构化数据格式，程序很容易读取。
- `JSON Mode`：尽量让模型直接输出标准 JSON 的方式。
- `Fallback`（兜底）：当理想方案失败时，系统自动退回次优方案。
- `Pydantic`：Python 数据校验工具，用来检查输出结构是否符合要求。
- `Validation`（校验）：检查数据结构和内容是不是符合预期。
- `Schema`（结构约束）：规定输出必须包含哪些字段、字段类型是什么。

## 3. 为什么项目2必须做模型对齐

如果项目2只是让模型写一段内容，模型偶尔输出得乱一点，可能问题不大。  
但项目2不是单点生成，它是一个工作流系统。

这里很多节点的输出都会被后面的节点继续消费，比如：

- research 的 topics 会被 writer 用
- writer 的 title / content / tags 会被 reviewer 用
- reviewer 的 score / passed 会被 approval 和 routing 用
- approval 的 decision 会决定最终流向

所以这里最大的风险不是“内容不够优美”，而是：

- 输出格式不稳定
- 下游无法解析
- 工作流路由出错

这就是为什么项目2一定要做模型对齐。

## 4. 项目2里哪些节点必须重点对齐

## 4.1 research 节点

research 不能只返回一段自然语言总结，它至少要稳定输出：

- `topics`
- 每个 topic 的标题
- 原因
- 热度或优先级

如果 research 输出不稳定，writer 就拿不到统一输入。

## 4.2 writer 节点

writer 不能只输出一大段文本，它至少要稳定输出：

- `title`
- `content`
- `tags`

否则 reviewer、export、平台适配都会很难消费。

## 4.3 reviewer 节点

reviewer 是项目2最需要结构化的节点之一。

它至少要输出：

- 吸引力分
- 准确性分
- 平台适配分
- 总分
- feedback
- passed

因为后面的条件分支要依赖它。

## 4.4 approval 节点

approval 也不能模糊，它至少要明确：

- `approve`
- `needs_edit`
- `reject`

否则主流程无法稳定路由。

## 5. 为什么不能只靠 prompt 说“请输出 JSON”

这是项目2模型对齐里最关键的一点。

很多人会觉得只要在 prompt 里写：

- “请严格输出 JSON”

就够了。

但真实情况通常不是这样，因为模型可能会：

- 在 JSON 前后加解释文字
- 漏字段
- 字段名写错
- 数值类型不对
- 输出半截 JSON

如果项目2只是给人看结果，这些问题也许还能忍。  
但项目2是工作流系统，后面还要继续被程序消费，所以不能只停留在“希望模型听话”。

## 6. 项目2当前推荐的三层对齐方案

## 6.1 第一层：`JSON Mode`

作用：

- 尽量让模型从一开始就按 JSON 格式输出

为什么先做这一层：

- 它能显著减少自由文本污染
- 对 workflow 系统来说，比自然语言输出更适合程序读取

## 6.2 第二层：手动解析

作用：

- 当模型输出里混入额外文本时，程序尝试把 JSON 提取出来

为什么要有这一层：

- 因为即使开了 `JSON Mode`，实际输出也不一定百分之百完美

## 6.3 第三层：`Pydantic` 校验

作用：

- 检查提取出来的 JSON 是否真的符合预期结构

例如：

- 字段全不全
- 类型对不对
- 值是否有效

为什么这层很关键：

- 没有校验，程序只会以为“拿到了 JSON 就可以”
- 但其实一个字段类型错了，也会让后面路由和导出出问题

## 7. 为什么这套方案适合项目2

因为项目2追求的不是“模型尽量聪明”，而是：

- 能稳定跑 workflow
- 能稳定进入下一节点
- 能稳定做分支判断
- 能稳定导出结果

所以三层方案很适合这个系统：

1. `JSON Mode` 负责提高前端输出稳定性
2. 手动解析负责提高容错能力
3. `Pydantic` 负责保证最终输入给系统的数据是真正可用的

## 8. `Fallback`（兜底）在项目2里怎么理解

`Fallback` 的意思不是“随便降级”。

在项目2里，它更准确的意思是：

> 当结构化输出失败时，系统仍然要尽量给出可继续运行的次优结果。

比如：

- research 解析失败时，至少回落到一个基础 topic
- writer 解析失败时，至少保留正文文本
- reviewer 解析失败时，至少回落到默认评分和基础反馈

为什么必须有 fallback：

- 因为项目2是工作流系统，不能每次一出错就整条链路崩掉

## 9. 这一步和项目2后面工程能力的关系

模型对齐不是孤立的，它会直接影响后面的：

- `LangGraph` 路由
- `PostgreSQL Checkpointer` 保存状态
- `SSE` 流式事件
- metrics 统计
- before / after 测量

因为如果输出都不稳定，后面这些工程能力会建立在摇晃的地基上。
