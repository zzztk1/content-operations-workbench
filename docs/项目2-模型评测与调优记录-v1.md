## 1. 这轮评测调优解决什么问题

这轮调优不是追求“所有指标都变好”，而是优先解决 Cursor 外部评估指出的两个真实问题：

1. `write_draft` 结构化直出不稳定。
2. 成本字段口径不够严谨，`Step Plan` 路线下不能继续用“按 token 估算成本”的方式假装有结果。

这两个点都满足项目2一开始定下的调优原则：

- 有真实模型链路。
- 有 before / after 对比。
- 有结果文件。
- 能明确说出优化收益和代价。

## 2. 关键名词解释

- `direct`
  - 模型直接输出了合法 JSON，程序一次就能解析。
- `salvage`
  - 模型没有老老实实只吐 JSON，但程序还是从正文或代码块里把 JSON 提出来了。
- `fallback`
  - 模型输出不够用，只能退回兜底结果。
- `TTFT`（Time To First Token，首字延迟）
  - 用户在流式输出里看到第一个字的时间。
- `MetricsContext`
  - 指标上下文管理器，用来统一记录节点级 token、延迟、错误数和成本口径状态。

### 3.1 评测对象

真实 `Step Plan` 路线下的 `LangGraph v2` 工作流，覆盖 3 个真实内容场景：

- 简历包装
- 工程化亮点讲述
- 面试表达

### 3.2 评测方式

统一使用固定设置，减少分支带来的随机性：

- `approval_decision=approve`
- `reviewer_threshold=15`
- `max_revisions=0`

这样做的原因：

- 先观察结构化输出本身，不让重写回路把结果放大得太随机。
- 保证 before / after 口径一致。

## 5. 这轮做了哪些调优动作

### 5.1 动作 A：收紧 `write_draft` 的原始 JSON 约束

做法：

- 改写 writer prompt，要求输出紧凑、明确、原始 JSON。
- 压缩文风提示，只保留更短的 `style_hints`。
- 把内容目标收敛成更短、更清晰的长度区间。

目标：

- 减少 writer 非结构化输出。
- 提高 `write_draft` 的 `direct` 比例。

### 5.2 动作 B：补 `DraftPayloadModel` 输入归一化

做法：

- 在 [schemas.py](F:/codex/codex1/projects/media-agent/src/langgraph_v2/schemas.py) 里给 `DraftPayloadModel` 增加预处理校验。
- 兼容常见字段变体：
  - `headline -> title`
  - `body / copy / draft_text -> content`
  - `channel -> platform`
- 自动把字符串 tags 转成列表。

目标：

- 降低“模型结构基本对，但字段名字略有变化”导致的误判。
- 让 writer 的结构化输出更稳定。

### 5.3 动作 C：把 `MetricsContext` 做成真代码能力

做法：

- 新增 [metrics_context.py](F:/codex/codex1/projects/media-agent/src/langgraph_v2/metrics_context.py)。
- 在 [engine.py](F:/codex/codex1/projects/media-agent/src/langgraph_v2/engine.py) 中统一记录节点级：
  - token
  - 延迟
  - 错误数
  - 成本口径状态

目标：

- 解决 Cursor 提到的“指标有，但口径不够扎实”问题。
- 让简历第 2 条从“概念”变成“真实代码实体”。

### 5.4 动作 D：修正 `Step Plan` 成本字段口径

做法：

- 在 `MetricsContext` 里显式新增：
  - `estimated_cost_available`
  - `cost_estimation_basis`
  - `price_per_1k_usd`
- 对 `Step Plan` 路线统一标记：
  - `estimated_cost_available = false`
  - `cost_estimation_basis = step_plan_subscription_not_token_billed`

目标：

- 不再用“`0.0` 成本”这种误导口径。
- 把“无法按 token 估算成本”这件事写清楚。

### 5.5 动作 E：失败实验并已回滚

实验内容：

- 给 repair 路由强行加 token 上限。

结果：

- 在 `Step Plan` 路线下引入稳定性风险。
- 出现多个节点 `exception-fallback`。
- 已回滚，不进入最终版本。

意义：

- 证明不是“限制越严越好”。
- 也证明这轮调优是保留有效项，而不是把所有尝试都包装成成功。

## 7. before / after 结论

### 7.1 变好的地方

- `direct_rate`
  - `11.11% -> 100%`
- `salvage_rate`
  - `88.89% -> 0%`
- `fallback_rate`
  - `0 -> 0`

  - `1/3 direct -> 3/3 direct`

  - `0/3 direct -> 3/3 direct`
- `review_structured`
  - `0/3 direct -> 3/3 direct`

### 7.2 变差的地方

- 平均延迟
  - `+23835.41 ms`
- 平均 prompt tokens
  - `-134.0`
- 平均 completion tokens
  - `+2485.67`
- 平均 total tokens
  - `+2351.67`
- 平均 `TTFT`
  - `+6079.02 ms`

### 7.3 这说明什么

这轮调优的真实结果不是“全面优化”，而是：

- 结构化输出稳定性显著提升。
- 代价是 completion token、总 token、延迟和 `TTFT` 都变差。

所以这轮最安全的项目口径是：

> 通过 prompt 收敛、schema 归一化和指标口径补强，显著提升了结构化直出率；但性能和 token 开销没有同步优化，因此这轮只能写“稳定性提升”，不能写“性能提升”。

## 10. 这轮调优的最终结论

这轮调优是有价值的，但它给出的不是单向好消息，而是一组清晰的取舍：

- 结构化输出显著更稳。
- `write_draft` 这个最关键的薄弱点已经在当前 3 场景 benchmark 里从 `0/3 direct` 提升到 `3/3 direct`。
- 但性能和 token 开销变差，所以不能把它包装成“全面优化”。

因此当前最准确的说法是：

> 项目2已经完成了真实模型评测与结构化调优，并通过 before / after 报告证明关键节点直出率显著提升；但性能和成本侧仍需继续优化，所以当前只写“稳定性提升”，不写“性能收益”。
