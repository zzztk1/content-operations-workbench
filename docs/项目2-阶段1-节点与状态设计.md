# 项目2阶段1：节点与状态设计

最后更新：2026-04-09

## 1. 这一步要解决什么问题

PRD 解决的是“这个产品为什么做、给谁做、要做到什么程度”。

节点与状态设计解决的是：

- 这条内容工作流到底拆成哪几个步骤
- 每一步负责什么
- 步骤之间靠什么数据衔接
- 哪些信息要被系统记住，方便审核、恢复、导出和回查

## 2. 先解释几个后面会反复出现的词

- `Node`（节点）：工作流中的一个处理步骤，比如 research、writer、reviewer。
- `State`（状态）：工作流在某一时刻携带的全部上下文数据。
- `StateGraph`（状态图）：用状态驱动节点流转的图式工作流结构。
- `SubGraph`（子图）：把主流程中的一段子流程单独拆出来管理。
- `Checkpointer`（状态持久化器）：把运行过程中的状态保存下来，支持恢复和回查。
- `Schema`（数据结构约束）：规定某段输入输出应该长什么样。

## 3. 为什么这个项目要做节点拆分

这个项目不能做成一个“大模型一次性写完”的黑盒流程，原因有三个：

1. 内容生产本身就是多阶段任务，不同阶段目标不一样。
2. 审核和审批必须单独存在，否则流程不可控。
3. 后面要接 `StateGraph`、`SubGraph`、`Checkpointer`、事件流和测量机制，必须先把边界拆清楚。

## 4. 主链路节点设计

## 4.1 `brief_intake`

职责：

- 接收用户输入的 `brief / platform / style`
- 生成本次运行的基础上下文
- 初始化状态对象

输入：

- `brief`
- `platform`
- `style`
- 可选审批配置

输出：

- 初始 `state`
- `run_id`
- `request_id`

为什么要有这个节点：

- 这一步把“用户输入”变成“系统上下文”
- 后面做回查和恢复时，必须知道一次运行最初长什么样

## 4.2 `research`

职责：

- 根据 brief 生成候选选题、角度或证据
- 形成后续写作的输入基础

输入：

- `brief`
- `platform`

输出：

- `topics`
- `selected_topic`
- `research_evidence`

为什么不能省略：

- 如果没有 research，writer 只能直接瞎写，内容稳定性会明显变差

## 4.3 `writer`

职责：

- 根据选题和平台风格输出第一版内容草稿
- 在重写场景下，吸收 reviewer 反馈做定向修改

输入：

- `selected_topic`
- `platform`
- `style`
- `review_feedback`（重写时）

输出：

- `draft.title`
- `draft.content`
- `draft.tags`

## 4.4 `reviewer`

职责：

- 对草稿做结构化评分
- 输出通过/不通过结论和修改建议

输入：

- `draft`
- `platform`

输出：

- `review.attraction_score`
- `review.accuracy_score`
- `review.platform_score`
- `review.total_score`
- `review.feedback`
- `review.passed`

为什么要独立出来：

- 它不是“再生成一版内容”，而是一个质量控制节点
- 这一步是后面重写回路的判断依据

## 4.5 `approval`

职责：

- 接住 reviewer 之后的人机协作决策
- 输出 `approve / needs_edit / reject`

输入：

- `review`
- 人工审批意图

输出：

- `approval.decision`
- `approval.note`
- `approval.at`

为什么不能直接让 reviewer 决定最终结果：

- reviewer 是质量判断，approval 是业务决策
- 有些内容“分数够”，但业务上仍可能不想发

## 4.6 `export`

职责：

- 把最终结果导出成可交付内容包
- 输出结构化文件和可读文件

输入：

- `draft / adapted`
- `review`
- `approval`

输出：

- `content_package.json_path`
- `content_package.markdown_path`

## 5. 为什么后面还要拆 `SubGraph`（子图）

当前先理解原则，不需要死记实现细节。

建议拆成 3 个子图：

### 5.1 `Research SubGraph`（研究子图）

包括：

- topic 生成
- evidence 合并

好处：

- 后面如果加外部搜索、Graph RAG、并发检索，不会污染主图

### 5.2 `Writing SubGraph`（写作子图）

包括：

- 草稿生成
- 平台适配

好处：

- 后面如果加多模型路由、并发生成、封面/素材扩展，也有清晰挂点

### 5.3 `Review / Approval SubGraph`（审核审批子图）

包括：

- 结构化审核
- 是否重写
- 是否审批通过

好处：

- 最能体现“AI 自动化 + 人工把关”的产品特色

## 6. 状态设计

## 6.1 为什么要做 `State`（状态）设计

因为这个项目不是单轮调用，它要跨多个节点流转。

系统必须记住：

- 用户一开始说了什么
- 中间生成了什么
- 审核出了什么问题
- 当前跑到哪一步了
- 有没有需要导出的结果

如果状态设计不清楚，后面就很难做：

- 重写回路
- run 恢复
- 历史回查
- 流式事件
- 指标测量

## 6.2 状态字段建议

### A. 身份字段

- `run_id`：一次完整运行的唯一标识
- `request_id`：一次请求级标识，方便日志追踪
- `thread_id`：后续给 `Checkpointer` 使用的线程标识

### B. 用户输入字段

- `brief`
- `platform`
- `style`

### C. 业务过程字段

- `selected_topic`
- `research`
- `draft`
- `review`
- `approval`

### D. 控制字段

- `status`
- `revision_count`
- `reviewer_threshold`
- `max_revisions`

### E. 观测字段

- `trace`
- `events`
- `metrics`
- `errors`

### F. 输出字段

- `content_package`

## 7. 这一步的设计原则

1. 节点按业务职责拆，不按代码文件拆。
2. 状态按流程需要设计，不按“先有什么变量”设计。
3. 人工审批必须保留为独立语义。
4. 后续所有工程能力，都要挂在节点和状态上，而不是临时硬塞。

## 8. 本阶段验收标准

- 你能说清楚每个节点负责什么，而不是只会背名字。
- 你能解释为什么 reviewer 和 approval 不能合并。
- 你能解释为什么这个项目必须有 state，而不是几个函数串起来就行。
- 你能说清为什么后面要拆 `SubGraph`。
