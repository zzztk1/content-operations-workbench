# 项目2-最初功能计划基线清单-v1

最后更新：2026-04-12

## 1. 作用

这份清单只做一件事：

> 把项目2最开始锁定的目标、功能计划和简历亮点，整理成一份可供 Cursor 对比验收的基线。

这样后面不管是验收测试、功能审计，还是让 Cursor agent 做外部评估，都不会只看“现在做了什么”，而是会同时对比：

- 最开始计划做什么
- 现在实际做到什么
- 哪些只是部分完成
- 哪些虽然做了，但口径要收一收

## 2. 最初总路线

项目2最开始锁定的是这条完整路线：

1. 需求分析
2. 模型预研
3. 数据准备
4. 模型设计
5. 模型对齐
6. 模型应用
7. 模型评测
8. 模型上线
9. 验收测试
10. 发布上线
11. 持续运营

## 3. 最初锁定的核心系统目标

项目2最开始锁定的核心目标是把旧版工作流升级成：

1. 真 `LangGraph StateGraph`
2. 真 `SubGraph`
3. 真 `PostgreSQL Checkpointer`
4. 真 `Mock` 开关体系
5. 真 `SlowAPI`、`/health`、`graceful shutdown`
6. 真 `JSON Mode + 手动解析 + Pydantic`
7. 真 `SSE / token 级事件流`
8. 真 before / after 基线测量
9. 真前后端体验入口
10. 真图片链路
11. 真视觉质检

## 4. 最初锁定的图片功能目标

图片功能不是后补装饰，而是原目标的一部分。最开始应该做到的是：

1. 把配图纳入工作流，不是导出后外挂
2. 有独立图片子图 `visual_subgraph`
3. `plan_cover -> generate_cover -> review_cover_visual`
4. 真实主图生成
5. 多候选图生成
6. 图片导出到结果包
7. 前端可展示主图和候选图
8. 支持 `image_mock` / 真实配图切换
9. 支持视觉质检 `vision_review_mock` / 真实视觉质检切换
10. 图片质量校验
11. 图片并发优化
12. 图片性能基线
13. 图文一致性检查
14. badcase 评测

## 5. 最初锁定的简历亮点基线

下面这 8 条，是最开始要尽量对齐的简历亮点方向。

### 1. 工作流与状态持久化

- 基于 `LangGraph` 构建多阶段内容生成工作流
- 用 `SubGraph` 拆选题、写作、配图
- 通过 `PostgreSQL Checkpointer` 做状态持久化
- 支持历史节点回查与增量重试
- 把故障恢复粒度从整图级细化到节点级

### 2. 指标采集与成本口径

- `MetricsContext` 记录节点级 token、时延、错误数
- 为模型选型与资源调优提供依据

说明：
- 这一条后面应优先写“指标采集与资源消耗分析”
- 不应默认写成精确美元成本核算，除非真有可靠账单口径

### 3. 流式输出与 TTFT

- `SSE` 流式输出
- token 级事件
- `TTFT` 捕获与优化
- 流式与非流式模式下结果一致性

### 4. 图片批量并发优化

- 图片批量生成场景
- `asyncio.gather + run_in_executor`
- 指数退避重试
- 串行/并发对比报告

说明：
- 这一条可以写“做了并发优化并完成真实测量”
- 不应预设写成固定 `70%`，必须跟最新报告绑定

### 5. 结构化输出与推理开销优化

- `JSON Mode + 手动解析 + Pydantic`
- 结构化输出兼容
- 降低 token 开销
- 降低单位请求资源消耗

说明：
- 这一条可以写“降低 token 开销 / 推理资源消耗”
- 不应默认写成固定“成本下降 40%”，除非账单口径成立

### 6. Mock 与调试效率

- `llm_mock`
- `image_mock`
- `checkpointer_mock`
- Swagger UI
- 本地调试提效

说明：
- `Ngrok` 是否写入简历，取决于后面是否真实做近公网联调

### 7. 可观测性

- `LangSmith`
- `request_id`
- 结构化日志
- 节点路径、State 注入、阶段耗时

### 8. 服务治理

- `SlowAPI`
- 熔断
- `/health`
- graceful shutdown
- 公网部署下的高可用基础能力

## 6. 最初锁定的验收口径

后面做验收时，至少应该按这几类判断：

1. 功能是否真实存在
2. 是否有结果文件
3. 是否有测量动作
4. 是否有 badcase 或边界验证
5. 简历口径是否需要软化

## 7. 给 Cursor 的对比要求

让 Cursor 对比时，必须按下面四列输出：

1. 最初计划
2. 当前实现
3. 当前证据
4. 结论
- 已完成
- 部分完成
- 已完成但需软化口径
- 未完成

## 8. 可直接补给 Cursor 的附加说明

如果你要把这份清单一起发给 Cursor，可以附一句：

> 请不要只按当前代码表面判断项目状态，而要严格对照“最初功能计划基线清单”逐项核对，输出哪些真正完成、哪些只是部分完成、哪些结果数字不能照写进简历。
