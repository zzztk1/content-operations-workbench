# 项目2阶段3：模型设计

最后更新：2026-04-09

## 1. 这一步要解决什么问题

需求分析解决的是“为什么做这个项目”，模型预研解决的是“底座怎么选”，数据准备解决的是“系统靠什么材料来写、测、改、证”。

模型设计这一步要继续回答：

- 这个系统为什么不能只靠一个 prompt 完成
- 为什么要拆成多个节点
- 每个节点到底负责什么
- 节点之间靠什么状态衔接

简单说，模型设计要把“产品流程”翻译成“系统结构”。

## 2. 先解释几个关键词

- `Prompt`：给模型的指令。
- `Node`（节点）：工作流里的一个处理步骤。
- `State`（状态）：系统在某一时刻保存的全部上下文信息。
- `Schema`（结构约束）：约定输入输出应该长什么样。
- `Trace`（执行轨迹）：记录系统执行过哪些步骤。

## 3. 为什么项目2不能只靠一个 prompt

如果项目2只是“给我写一篇小红书文案”，那一个 prompt 可能就够了。

但项目2不是这个目标。

项目2真正要做的是：

- 接 brief
- 研究选题
- 生成内容
- 审核内容
- 根据反馈重写
- 人工审批
- 导出内容包

这 7 件事的目标不一样，输出格式也不一样。

如果硬塞进一个 prompt，会出现几个问题：

1. 可控性很差  
你很难知道到底是哪一步出了问题。

2. 很难重写  
如果审核不通过，你没法只改“写作部分”，通常只能整段重来。

3. 很难测量  
你不知道 research 慢，还是 writer 慢，还是 reviewer 慢。

4. 很难恢复  
如果流程中断，没有清晰状态点可恢复。

所以项目2必须从“一次性生成”升级到“多节点工作流”。

## 4. 节点设计

## 4.1 `brief_intake`

职责：

- 把用户输入转成系统能理解的运行上下文
- 初始化本次运行的基础状态

为什么要有这个节点：

- 这一步不是在生成内容，而是在建立运行边界
- 后面做回查和恢复时，必须知道这次运行最初输入了什么

## 4.2 `research`

职责：

- 把 brief 转成候选主题、角度和研究结果
- 给 writer 提供更清晰的输入

为什么要单独拆出来：

- 没有 research，writer 就只能直接根据 brief 生写，结果容易泛化
- research 可以作为后续 Graph RAG 和外部搜索增强的入口

## 4.3 `writer`

职责：

- 根据选题、平台、风格生成内容草稿
- 在重写场景下，根据 reviewer 反馈做定向修改

为什么是核心节点：

- 它承担的是主要内容产出
- 但它不能独自决定最终输出是否可交付

## 4.4 `reviewer`

职责：

- 对内容做结构化评分
- 给出修改意见
- 决定是否进入重写回路

为什么要独立：

- reviewer 不是“再生成一版内容”，而是专门负责质量判断
- 它是工作流里最重要的质量控制点

## 4.5 `approval`

职责：

- 承接人工业务决策
- 输出 `approve / needs_edit / reject`

为什么不能和 reviewer 合并：

- reviewer 解决“内容质量行不行”
- approval 解决“业务上发不发”

这两个判断在真实内容运营里并不完全相同。

## 4.6 `export`

职责：

- 把最终结果导出成结构化内容包和可读文件
- 形成项目可交付产物

为什么重要：

- 如果没有 export，项目就停留在“模型跑了一次”
- 有了 export，项目才有“可交付系统”的味道

## 5. 为什么还要设计状态（State）

节点拆完之后，系统还需要一个“贯穿始终的上下文容器”。

这个容器就是 `State`。

项目2里的 State 至少要记住：

- 用户输入了什么
- research 产出了什么
- writer 生成了什么
- reviewer 打了多少分
- 是否已经重写过
- approval 做了什么决定
- 最终导出了什么

如果没有 State，后面很多能力都做不稳：

- 重写回路
- run 恢复
- 历史回查
- trace 记录
- metrics 统计

## 6. 状态字段为什么这样分

## 6.1 身份字段

包括：

- `run_id`
- `request_id`
- `thread_id`

作用：

- 标识一轮完整运行
- 串联日志、状态保存和回查

## 6.2 输入字段

包括：

- `brief`
- `platform`
- `style`

作用：

- 记录本次任务最原始的业务上下文

## 6.3 业务过程字段

包括：

- `selected_topic`
- `research`
- `draft`
- `review`
- `approval`

作用：

- 记录每个业务节点的核心产物

## 6.4 控制字段

包括：

- `status`
- `revision_count`
- `reviewer_threshold`
- `max_revisions`

作用：

- 让系统知道当前在什么阶段
- 让重写逻辑有明确边界

## 6.5 观测字段

包括：

- `trace`
- `events`
- `metrics`
- `errors`

作用：

- 支撑后面的流式输出、可观测性和性能测量

## 7. 为什么模型设计这一步是项目2的核心

项目2和普通内容工具最大的区别，不是“模型更强”，而是：

- 工作流结构更清楚
- 节点职责更明确
- 状态语义更完整

也就是说，这一步决定的不是一段 prompt，而是这个系统是不是一个真正的工作流产品。

## 8. 本阶段验收标准

- 你能说清为什么项目2不能只靠一个 prompt。

- 你能说清 State 的作用，以及为什么状态字段必须分层。
