# 项目2-生图能力五阶段补充-v1

## 1. 模型预研

### 这一步要补什么
- 先确认“生图”不是继续靠文本模型硬做，而是拆成图片生成模型与视觉质检模型两条线。
- 文本主线继续用 `step-3.5-flash` 做 brief 理解、配图 prompt 生成、封面文案策划。
- 图片生成主线单独用 `step-2x-large` 做封面图与候选图生成。
- 视觉质检主线单独用 `step-1o-turbo-vision` 做图文一致性、可读性、构图与风险项检查。

### 为什么现在就要定
- 因为如果这一层不先拆清楚，后面会把“会写 prompt”和“会真的生图、看图”混成一件事。
- 这一步的本质是把图片能力的模型边界先钉死。

### 当前项目2对应结论
- `step-3.5-flash`：负责文本与配图策划。
- `step-2x-large`：负责真实生图。
- `step-1o-turbo-vision`：负责视觉质检。

### 面试稿
- “项目2里我没有把生图继续塞给文本模型，而是提前拆成了三段：文本模型负责配图策划，图片模型负责真实生成，视觉模型负责看图质检。这样后面做工作流和评测时，能力边界会更清楚。”

## 2. 模型设计

### 这一步要补什么
- 把生图正式纳入主工作流，而不是挂在导出后面做临时增强。
- 新增图片子图 `visual_subgraph`，节点顺序为：
  - `plan_cover`
  - `generate_cover`
  - `review_cover_visual`
- 状态里要补这些字段：
  - `image_plan`
  - `image_asset`
  - `cover_candidates`
  - `cover_visual_review`
  - `text_image_consistency`

### 设计原则
- `plan_cover` 只负责生成结构化图片方案，不直接生图。
- `generate_cover` 只负责调图片模型与产出图片资产。
- `review_cover_visual` 只负责质检与打分，不负责再写正文。
- 这样文本工作流和图片工作流是并联协作，不会互相污染。

### 面试稿
- “我在模型设计阶段把生图做成了独立子图，而不是临时插一个生图函数。这样封面策划、真实生图和视觉质检分别有自己的节点和状态字段，后面才方便做并发、导出和质量评测。”

## 3. 模型对齐

### 这一步要补什么
- 让生图链路也从‘能跑’变成‘结构稳定、结果可消费’。
- `plan_cover` 输出固定 schema：
  - `prompt`
  - `negative_prompt`
  - `overlay_text`
  - `visual_style`
  - `aspect_ratio`
- `review_cover_visual` 输出固定 schema：
  - `theme_match_score`
  - `readability_score`
  - `composition_score`
  - `overall_score`
  - `passed`
  - `risk_flags`
  - `feedback`

### 对齐方法
- 配图策划节点：继续用 `JSON Mode + 手动解析 + Pydantic`。
- 视觉质检节点：输出短结构化 JSON，避免长解释污染下游。
- 图片侧补启发式图文一致性检查，作为低成本兜底层。

### 当前项目2对应成果
- `image_plan` 已结构化。
- `cover_visual_review` 已结构化。
- badcase 里已经覆盖：
  - `block_theme_mismatch`
  - `title_zone_unreadable`
  - `composition_chaotic`

### 面试稿
- “项目2在模型对齐阶段，不只是约束正文输出，也约束了生图链路。封面策划和视觉质检都必须返回结构化结果，这样图片能力才能真正进入工作流，而不是停留在一张图好不好看这种主观判断上。”

## 4. 模型应用

### 这一步要补什么
- 把图片链路真正接进 API、前端和导出结果。
- API 支持请求级切换：
  - `image_mock`
  - `vision_review_mock`
  - `cover_candidate_count`
- `/demo` 支持：
  - 真实配图 / Mock 配图切换
  - 视觉质检切换
  - 多候选图展示
  - 主图展示

### 当前项目2已完成的应用能力
- 真实图片模型：`step-2x-large`
- 多候选图：1 到 4 张
- 图片导出：`outputs/images/*.png`
- 图片静态访问：`/outputs/images/...`
- 视觉质检结果接入导出包、前端预览、SSE final 事件

### 面试稿
- “项目2在模型应用阶段，我把生图从预留能力补成了真实链路。现在前端可以直接切真实配图和视觉质检，后端则会把主图、候选图和质检结果一起导出，所以它已经不是文本系统外挂一张图，而是完整图文工作流。”

## 5. 模型评测

### 这一步要补什么
- 生图能力也必须像文本能力一样，有 before/after、质量报告和 badcase。
- 至少要有 4 类结果：
  - 图片接入可用性
  - 图片质量校验
  - 图片并发对比
  - 视觉质检 real / mock / badcase

### 当前项目2已落的结果文件
- 图片接入与可用性：
  - `latest_real_visual_workflow_report.json`
  - `latest_api_real_visual_workflow_report.json`
- 图片质量：
  - `latest_image_asset_quality_report.json`
- 图片并发：
  - `latest_image_batch_compare_report.json`
  - `latest_image_performance_baseline.json`
- 视觉质检：
  - `latest_visual_review_mock_report.json`
  - `latest_visual_review_real_report.json`
  - `latest_visual_review_badcase_report.json`

### 当前能成立的评测口径
- 可以写：
  - 真实图片链路已接通
  - 多候选图已接通
  - 图片并发优化已测量
  - 视觉质检已接入并完成 badcase 验证
- 不能写过头：
  - 图片成本固定下降多少
  - 视觉质检准确率多少
  - 图片质量自动闭环修复

### 面试稿
- “项目2在模型评测阶段，我没有把图片能力只当演示效果，而是给它补了独立评测。现在图片链路已经有可用性、质量、并发和视觉 badcase 四类结果文件，所以这部分不是一句‘支持配图’，而是有证据链的。”

## 最短总复述

- 预研：先拆清文本、生图、看图三类模型。
- 设计：把生图做成子图和状态字段。
- 对齐：把封面策划和视觉质检都做成结构化输出。
- 应用：把真实配图、多候选图、视觉质检接进 API 和前端。
- 评测：给图片链路补可用性、质量、并发和 badcase 报告。

## 最短面试总稿

- “我后来把项目2的生图能力按五个阶段完整补齐了。预研阶段先拆清文本模型、图片模型和视觉模型；设计阶段把生图做成独立子图；对齐阶段让封面策划和视觉质检都返回结构化结果；应用阶段接进真实 API、前端和导出；评测阶段再补图片质量、并发和 badcase 报告，这样图片能力才能真正写进简历。”
