## 2. 为什么要做这个项目

### 2.1 业务问题

目标用户不是“想玩 AI 的人”，而是有明确内容生产任务的人：

- 个人创作者需要更快地找到可发选题，并把内容写得更像平台原生内容。
- 小团队运营需要在少人力下稳定地产出内容，而不是完全靠个人状态。
- 代运营或多账号运营需要一套能复用、能回查、能审稿、能导出的流程。

他们的典型痛点不是“不会写一句文案”，而是：

- 不知道今天该写什么
- 同一主题跨平台改写很费时间
- AI 直接生成的内容质量不稳定
- 团队缺少统一的审核和返工机制
- 多个工具拼起来能用，但过程不透明，也很难复盘

### 2.2 为什么这个题目适合做成项目2

这个题目适合项目2，不只是因为“看起来像个 Agent 项目”，而是因为它天然包含了适合做成工程亮点的链路：

- 有明显的多阶段流程，不是单轮问答
- 有人机协作点，适合做审批与恢复
- 有结构化输入输出，适合做 schema 校验
- 有内容生成和改写，适合做模型路由与 JSON fallback
- 有长流程状态，适合做 checkpoint 与 run 恢复
- 有可观测空间，适合做事件流、metrics、TTFT、健康检查

换句话说，这不是“为了套 LangGraph 而找场景”，而是这个场景本身就适合用图工作流来建模。

## 3. 为什么要用大模型

### 3.1 适合用大模型的部分

这个项目里最难的不是“把步骤串起来”，而是这些高不确定性任务：

- 从 brief 中理解真正的内容目标
- 生成候选选题并解释理由
- 根据平台风格生成更像原生内容的草稿
- 对内容进行多维审核并提出改写建议
- 按平台风格进行重写和适配

这些都不是纯规则系统擅长的事情，因为它们依赖：

- 语义理解
- 风格迁移
- 不完整需求补全
- 对模糊目标的结构化输出

### 3.2 不适合完全交给大模型的部分

但这也不意味着“全部丢给一个模型”。

真正可用的产品应该把不确定性交给模型，把确定性交给工程系统：

- 流程编排交给 LangGraph
- 状态持久化交给 Postgres Checkpointer
- 审批分支交给显式条件路由
- 结构化结果交给 JSON mode + 手动解析 + Pydantic
- 历史回查交给持久化层
- 稳定性治理交给 `/health`、限流、熔断、Mock 开关

所以这里的正确姿势不是“做一个大模型应用”，而是“做一个以大模型为核心能力、但被工程流程约束住的系统”。

## 4. 为什么不直接用成熟产品

这里要先分两类看。

### 4.1 成品型工具

代表：Jasper、Copy.ai、Notion AI 一类内容创作/营销工具。

这类工具的优点很明显：

- 上手快
- 模板丰富
- 对运营团队友好
- 很适合直接拿来生产内容

但它们不适合当这个项目的最终路线，原因也很明确：

- 你能用，但你很难证明“系统怎么编排的”。
- 你可以产出内容，但很难把 `LangGraph + SubGraph + PostgreSQL Checkpointer` 这些工程亮点写成自己的实现。
- 你能获得业务结果，但拿不到你自己可控的底层事件流、checkpoint 恢复、结构化校验链路。
- 它们更像“买工具解决业务问题”，而不是“做出一个可复现的 AI 工程化项目”。

对项目2来说，成熟产品更适合做“竞品与替代方案”，而不是最终交付方案。

## 5. 为什么不直接用 Coze / Dify / Zapier 这类平台先搭一个

### 5.1 平台方案的真实优点

Coze、Dify、Zapier Agents 这类平台确实很强，适合快速试错：

- 可以拖拽式编排工作流
- 能接知识库、工具、外部应用
- 能很快做出可演示原型
- 对非工程用户非常友好

如果你的目标只是“1 天做个 demo 给老板看”，平台路线通常更优。

### 5.2 但这次我们为什么不走平台路线

这次项目2的目标不是“做一个能跑的 demo”，而是“做一个原版 PDF/简历可写的工程项目”。这就决定了平台方案有几个根本问题：

#### 问题1：平台工作流不等于你自己的工程能力

你在 Coze 或 Dify 上搭出一条流程，能证明你会做 AI 工作流原型，但很难证明：

- 你真的实现过 `LangGraph StateGraph`
- 你真的做过 `PostgreSQL Checkpointer`
- 你真的做过事件流、恢复、稳定性治理

也就是说，平台更适合“产品原型能力证明”，不够适合“底层工程能力证明”。

#### 问题2：你对 runtime 的可控性不够

项目2这次锁定的亮点里，有不少就是平台层很难完全按你想要的方式表达的：

- SubGraph 拆分方式
- Postgres 级持久化与恢复语义
- 节点事件流与 TTFT 测量
- JSON mode + 手动解析 + Pydantic 校验
- Mock 开关体系
- `/health` + 限流 + 熔断

这些不是“平台完全做不到”，而是：

- 你能不能做到，取决于平台边界
- 你做出来后，能不能说清楚是你自己实现的，也不够稳

#### 问题3：简历含金量不一样

如果项目最终描述变成：

- “基于某低代码平台搭建了一个内容工作流”

和：

- “基于 LangGraph StateGraph 自研多阶段内容运营系统，引入 PostgreSQL Checkpointer、SubGraph、SSE 事件流、JSON fallback 与稳定性治理”

这两种表达在面试中的追问深度和说服力完全不同。

### 5.3 平台路线在这个项目里的正确定位

平台不是没用，而是不该做最终交付形态。

更合理的定位是：

- Coze / Dify：可以作为需求验证或交互原型参考
- 项目2最终版：必须是可运行、自持久化、可测量、可验收的代码项目

## 6. 竞品与替代方案判断

| 方案类型 | 代表产品 | 适合什么 | 不适合什么 | 对项目2的结论 |
|---|---|---|---|---|
| 成品型内容工具 | Jasper、Copy.ai | 快速产出营销内容、统一品牌语气、交付给运营直接用 | 很难证明底层编排、checkpoint、恢复、观测等是你自己的实现 | 用来做竞品分析，不作为最终方案 |
| 平台型 Agent/Workflow | Coze、Dify、Zapier Agents | 快速搭原型、低代码试错、连知识库和外部工具 | 平台边界强，底层控制弱，简历里很难稳写“真 LangGraph + Postgres” | 可参考，不作为最终方案 |
| 自研工程方案 | LangGraph + Postgres + FastAPI/Streamlit | 可控、可测量、可恢复、可观测，能形成工程证据链 | 开发成本更高，需要你亲手走完整个实现过程 | 这是本项目锁定路线 |

## 7. 最终产品决策

### 7.1 我们做的不是“AI 写作工具”

项目2最终的产品定义应该是：

> 一个面向自媒体运营场景的、可恢复、可观测、可审批、可导出的 Graph RAG 内容工作流系统。

### 7.2 我们选择自研的核心原因

- 业务上：这个场景真的需要多阶段协作，不是单轮生成。
- 产品上：我们要保留人工审批、返工、导出、回查，而不是追求“全自动一键发文”。
- 工程上：项目目标明确要求真迁 `LangGraph + PostgreSQL Checkpointer`，平台型方案无法稳定承载这条简历表达。
- 复现上：你需要亲手走完整条链路，后续面试才扛得住追问。

## 8. 这一阶段给你的结论

如果你现在问“这项目值不值得继续做”，答案是值得，但要明确它不是一个“内容生成小工具”，而是一个用内容运营场景承载工程化 Agent 能力的项目。

如果你问“为什么不用现成产品”，答案是：

- 现成产品更适合直接干活
- 平台工具更适合快速原型
- 但你这次要复现的是“能写进简历、还能经得起追问的工程系统”，所以最终必须自研

## 10. 本步骤拆分面试稿

### 10.1 需求分析面试稿

我当时先判断的不是“模型能不能写文案”，而是内容运营里真正低效的环节是什么。最后我把问题收敛成 5 个动作：选题、写作、审核、审批、导出，这样后面系统设计就不会跑偏。

### 10.2 为什么用大模型面试稿

这个项目里最适合用大模型的部分，是理解 brief、生成候选选题、按平台风格写内容、再根据审核意见重写。因为这些任务都依赖语义理解和风格迁移，不是纯规则模板能稳定解决的。

### 10.3 竞品分析面试稿

我看过现成内容工具和平台型工作流产品，它们确实能更快出结果，但大多停留在“帮你生成内容”或者“帮你拼流程”。我的目标不是买一个工具，而是做一个能把状态、审批、恢复和观测都沉淀下来的工程系统。

### 10.4 为什么不用 Coze / 平台搭面试稿

Coze、Dify 这类平台适合快速原型，但它们更像平台能力，不完全等于我自己的底层工程能力。因为这次我要对齐的是 LangGraph、Postgres Checkpointer、事件流和稳定性治理，所以最终还是要落到自研代码方案。

### 10.5 本阶段一句话总结

这一步我做的核心决策，不是“选哪个模型”，而是先确定这个项目必须是一套自研的内容工作流系统，而不是一个单点写作工具或低代码 Demo。
