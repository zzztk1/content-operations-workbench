# 项目2阶段5：模型应用
最后更新：2026-04-09

## 1. 这一步要解决什么问题

前面的几步已经分别解决了：

- 为什么要做这个项目
- 这个项目的数据从哪里来
- 模型在系统里怎么分工
- 模型输出怎样才能更稳定

模型应用这一步要解决的是：

> 这些已经定好的能力，怎么真正接进系统里，变成一个能运行、能演示、能继续迭代的内容工作流。

对项目2来说，这一步不是简单“调用一下大模型”，而是开始把下面几层真正接到一起：

- 阶跃星辰 API（StepFun API）
- LangGraph 工作流
- 状态 State
- PostgreSQL Checkpointer
- Mock 开关
- 流式输出与基础服务接口

## 2. 先解释几个关键名词

- `Application Layer`（应用层）：真正把模型能力包装成可使用系统的这一层。
- `Invoke`（调用）：把输入送进模型或工作流，拿回结果。
- `Compile`（编译图）：把定义好的图结构整理成可执行的工作流对象。
- `Endpoint`（接口端点）：系统对外暴露的访问入口，例如 `/run`、`/health`。
- `Mock`（模拟模式）：不用真实外部依赖，直接返回可控假数据的运行方式。
- `Streaming`（流式输出）：结果不是最后一次性返回，而是边执行边持续输出事件。
- `SSE`（Server-Sent Events，服务端推送事件）：一种常见的流式输出方式，服务端可以持续往前端推送事件。

## 3. 为什么项目2的模型应用不能只写一个调用脚本

如果项目2只是“输入一句话，生成一段文案”，写一个简单脚本就够了。

但项目2不是单点生成，而是一个工作流系统。它后面要同时满足：

- 多节点流转
- 条件分支
- 审核重写
- 状态保存与恢复
- 输出结构化结果
- 对外提供接口
- 后续做流式事件和评测

所以这里的“模型应用”，本质上是：

> 把模型从一个单独调用，提升成系统中的工作流能力。

## 4. 这一步的核心应用结构

### 4.1 模型服务层

当前项目2的主模型入口，是阶跃星辰 `Step Plan` API。

它在这一层主要负责：

- 解析 brief
- 生成 research 结果
- 生成 writer 内容
- 生成 reviewer 评分与反馈

为什么先统一一个主模型入口：

- 先把主链路跑稳，比一开始同时接多个供应商更重要
- 这样后面测工作流问题时，不会被多模型差异干扰
- 后续如果要做多模型增强，也更容易在同一抽象层扩展

### 4.2 工作流编排层

这一层后面用 LangGraph 来承接。

它的职责不是“让模型更聪明”，而是：

- 把多个节点按顺序串起来
- 根据状态决定分支
- 让研究、写作、审核、审批这些步骤形成一条完整链路

对项目2来说，LangGraph 的价值在于：

- 这是一条天然多节点的内容工作流
- 后面还有 SubGraph、条件边、恢复执行这些需求
- 手写流程虽然能跑，但很难优雅支撑后续工程化能力

### 4.3 状态与持久化层

这一层由 State 和 PostgreSQL Checkpointer 共同承担。

它负责保存：

- 本次运行输入了什么
- 当前跑到了哪个节点
- 中间产出了什么结果
- reviewer 和 approval 做了什么判断
- 最终导出了什么

为什么这层在模型应用里很重要：

- 没有状态，工作流只是“连续调用”
- 有了状态，工作流才真正变成“可恢复、可回查、可度量”的系统

### 4.4 服务接口层

这一层后面会提供：

- 触发运行的接口
- 查看状态的接口
- 健康检查接口 `/health`
- 流式事件接口

它的作用是让项目2从“本地脚本”逐步变成“可演示、可接前端、可测试”的应用系统。

## 5. 为什么模型应用这一步要保留旧版 baseline

先解释：

- `baseline`（基线）：当前可运行版本，后续所有优化都拿它做对照。

项目2现在已经有一版：

- 自定义状态机
- SQLite checkpoint
- 可运行主链路
- 有基本验证脚本

这版虽然不是最终目标，但不能直接推翻，原因有三个：

### 5.1 它是功能对照组

后面你要证明 LangGraph 版更好，必须先有一个稳定的旧版对照。

### 5.2 它是迁移安全网

如果新版一开始就不稳定，旧版还能继续跑验证和演示。

### 5.3 它是 before / after 测量基础

后面所有“迁移前后变化”都要基于 baseline 去比较。

所以项目2的正确做法不是“直接把旧版删掉”，而是：

> 旧版保留成 baseline，新版并行推进成主目标实现。

## 6. 为什么新版要并行接入，而不是直接大改现有主链路

这是项目2模型应用阶段很关键的工程策略。

我更推荐：

- 旧版链路继续保留
- 新版在独立目录和独立入口下搭建
- 等新版主链路稳定后，再逐步接管

这样做的原因是：

- 避免改一半时把现有可运行版本弄坏
- 方便做同输入对照测试
- 方便把问题明确归因到“新工作流”而不是“旧功能回归”

这也是为什么前面已经先准备了 `langgraph_v2` 这样的轻量骨架，但没有直接把旧版主链路替换掉。

## 7. 项目2这一步实际要接的东西

## 7.1 接入新的 LangGraph 主链路

这一步的目标不是一次性做完全部功能，而是先把新版主链路立起来。

第一批至少包括：

- 统一 State schema
- 主图入口
- research / writer / reviewer / approval / export 的基本节点映射
- 条件分支骨架

## 7.2 接入 Mock 开关体系

为什么这一步要先做 Mock：

- 项目2后面很多调试不应该每次都打真实模型
- 接 Postgres、流式输出、限流时，也需要可控输入

Mock 在这里的价值是：

- 让你在不依赖外部服务的情况下调工作流结构
- 让 benchmark 更稳定
- 让演示更可控

## 7.3 为 PostgreSQL Checkpointer 预留接口

这一阶段不一定要把所有数据库细节一次到位，但至少要把接口位置定清楚：

- checkpointer 在哪里初始化
- graph 在哪里绑定 checkpointer
- run_id / thread_id 怎样传递

为什么模型应用阶段就要考虑它：

- 因为它不是后面随手加的一层，而是会影响工作流运行方式

## 7.4 为流式输出预留事件口

项目2后面会做流式输出，所以现在应用结构里就要考虑：

- 节点开始事件
- 节点完成事件
- 中间状态更新事件
- 最终完成事件

这样后面接 `SSE` 或 `astream_events` 时，不需要再推翻链路。

## 8. 这一步的成果应该长什么样

模型应用这一步的阶段成果，不要求“所有工程能力一次性全部实现”，但也不能只停留在讲清结构和预留接口。

如果放在项目2的推进顺序里，这一步至少要出现一个真正可运行的 MVP。

这里说的 MVP，至少包括：

- 新版 LangGraph 主链路能独立运行
- 主链路里已经接入真实模型入口或可控 Mock
- 至少一个 `SubGraph` 已经真正参与执行
- 关键节点已经使用结构化输出约束
- `PostgreSQL Checkpointer` 已经真正接到运行链路
- 至少有一个脚本或 API 入口能触发完整运行
- 至少产出一次真实运行结果文件

只有满足这些条件，项目2才算真正完成了“模型应用”这一步。

在此之前，更准确的说法应该是：

> 正在完成模型应用，不应该提前进入模型评测。

在满足 MVP 的前提下，这一步还应继续带来下面这些清晰变化：

- 项目2开始从脚本型 demo 过渡到应用型系统
- 新旧两套链路的角色分工变清楚
- 新版 LangGraph 入口开始具备承接主流程的能力
- Mock、Checkpointer、流式事件这些后续能力有明确接入点

换句话说，这一步最重要的成果是：

> 系统已经不只是“设计好了”，而是开始拥有可落地的应用骨架。

## 9. 这一步还没有完成什么

这一步虽然开始进入应用层，但还没有等于“全部做完”。

还没完成的包括：

- LangGraph 主链路还没有完全替代旧版状态机
- `LangSmith` 远端观测还没有在这一阶段写入“已完成”结论
- 生产级成本对账还没有完成
- before / after 测量已经形成脚本化闭环，但还没有扩展到 token 优化前后对比指标

所以这一步的性质是：

- 应用骨架开始落地
- 但核心工程能力仍然要在后续步骤继续补全

## 10. 本阶段验收标准

- 你能解释清楚“模型应用”在项目2里不是单独调模型，而是把模型放进工作流系统里。
- 你能说清楚为什么旧版 baseline 不能删。
- 你能说清楚为什么新版要并行接入，而不是直接重构旧版。
- 你能解释清楚主模型层、工作流层、状态持久化层、服务接口层分别在做什么。

- 新版 MVP 必须真实跑通；如果还没有跑通，就不能把这一步标记为完成。

## 11. 下一步衔接

模型应用之后，下一步进入：

- 模型评测

在项目2里，这一步会重点回答：

- 新版链路到底比旧版提升了什么
